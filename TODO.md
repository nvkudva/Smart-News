- [ ] P1: collapse the two schema declarations into one. src/lib/schema-local.ts declares the local SQLite schema as a SCHEMA const plus an ADDED_COLUMNS list; src/lib/schema-d1.ts declares the D1 schema as an exported SCHEMA const plus an ADDED_COLUMNS list. D1 is SQLite, so this is one schema written twice in two shapes, and the only thing reconciling them is indexDrift() in src/lib/schema-d1.ts, which readFileSync's src/lib/schema-local.ts and regexes `CREATE INDEX IF NOT EXISTS (\w+)` out of its source text. It checks indexes only, and three had already drifted before it existed — one of them clusters_place, on the deployed read path. Measured diff on 19 Sep: 8 of 11 tables are column-for-column identical (articles, clusters, events, place_aliases, places, prefs, saved, sources); dirty and local_meta are local-only bookkeeping, sync_meta is D1-only. Beyond the table list, the full DDL text differs in five places, all in two tables: articles.url is `TEXT NOT NULL UNIQUE` locally and `TEXT NOT NULL` on D1; articles.fetched_at is `NOT NULL` locally and nullable on D1; and articles.source_id, articles.cluster_id and clusters.place_id carry REFERENCES locally and not on D1. The two constraint gaps have no comment anywhere and are almost certainly the same drift — the url one matters because src/lib/ingest.ts treats the URL as the identity while the sync upserts ON CONFLICT(id), so two rows with one URL are impossible locally and possible in D1; the fetched_at one matters because hydrate reads D1 into the local file and a null there fails the local NOT NULL insert. FINAL APPROACH: one src/lib/schema.ts holding TABLES (name -> column DDL), INDEXES, MIGRATIONS (ordered, replayed by both targets, absorbing ADDED_COLUMNS and the three DROP INDEX IF EXISTS renames that live in SCHEMA today), and two separate exception lists — LOCAL_ONLY_TABLES = {dirty, local_meta}, LOCAL_ONLY_INDEXES = {articles_hash}, D1_ONLY_TABLES = {sync_meta} — kept separate because today's LOCAL_ONLY mixes a table set with an index name and a table filter would silently skip the index check. db.ts:migrate() renders everything not D1-only and execs it in one go; applySchema renders everything not local-only and sends one statement per request, same strings through different transports. Order is TABLES -> MIGRATIONS -> INDEXES always, which makes db.ts's deferred clusters_place index (it is emitted after the ALTERs because on an old file the column does not exist when the CREATE block runs) stop being a special case. REFERENCES is rendered for the local target only, via a marker the D1 renderer strips: Cloudflare's docs state D1 enforces foreign keys by default, "identical to the behaviour you would observe when setting PRAGMA foreign_keys = on in SQLite for every transaction", so the scripts/d1/sync.ts comment saying D1 does not enforce them is true only because none are declared there. Emitting them to D1 is harmless today (CREATE TABLE IF NOT EXISTS no-ops on the live tables) but would arm a failure the moment articles is ever rebuilt, because the sync pushes articles before clusters and every new article whose cluster_id points at an unpushed cluster would fail the constraint. SCHEMA_VERSION must hash the rendered D1 DDL rather than the shared source, or a local-only edit re-stamps D1 for nothing. indexDrift() and scripts/d1/check.ts both delete, because drift stops being possible rather than being detected — but scripts/d1/migrate.ts --check must keep emitting steps.schema.outputs.needed, since .github/workflows/deploy.yml gates the migrate step on it and breaking that output is a failure that looks like success. RISK: low, and unusually verifiable, because both sides render to strings. CREATE TABLE IF NOT EXISTS cannot alter an existing table, so the whole TABLES half is a no-op against production whatever it renders; the only statements that can change prod D1 are the guarded ALTERs and the index renames, all of which run today unchanged. No rows move and no table is rebuilt. The real exposure is (a) fresh-database creation, because cycle.yml rebuilds the local store from schema-local.ts's DDL on an Actions cache miss, so a rendering error stays invisible in steady state and surfaces days later, and (b) the ADDED_COLUMNS -> MIGRATIONS collapse, where a dropped or reordered column silently misses on an old database — keep the existing PRAGMA table_info guard before each ALTER, which is idempotent and order-independent. VERIFY in this order before merging: byte-diff the rendered output of each target against today's SCHEMA and today's migrate() body; build a fresh local DB on old and new code and diff `SELECT sql FROM sqlite_master ORDER BY name`; run the new migrate against a copy of the real store and diff sqlite_master against the same copy run through the old one, which covers the old-database path the fresh test does not; run `bun run migrate:d1 --check` against prod (read-only) and confirm it still prints "Columns up to date" and emits its output line; dispatch one cycle before trusting it. If the first three come back byte-identical the change is provably a no-op on every database that exists. Rollback is `git revert` plus one sync — the stamp stops matching, applySchema re-runs, and the DDL is idempotent, so it self-heals. OUT OF SCOPE, deliberately: adding url UNIQUE and fetched_at NOT NULL to the live D1 articles table. That needs a create-copy-rename on a live table and is the only irreversible part, so it must not ride along with the refactor. When it is considered separately, lean against url UNIQUE — the owner lookup in ingest.ts already prevents duplicates locally so D1 only ever receives what local allowed, and a violation would fail the sync mid-push and stale the feed, which is worse than a duplicate row on a database the site only reads. fetched_at NOT NULL is the one worth closing, since that gap is what crashes hydrate.
